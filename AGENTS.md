# AGENTS.md

This file guides AI agents (Claude Code, Codex, OpenCode, …) working **in this repository**.
`CLAUDE.md` only imports this file — edit here, never there.

## What this repo is

The **single source of truth for Elf Express team conventions** — skills (rules an AI follows)
and agents (AI helpers that apply those rules) — fanned out by the
[`skillshare`](https://github.com/runkids/skillshare) CLI into every AI tool on each teammate's machine.

- **Team conventions only.** Nothing personal goes in here.
- It is not an application: no build/test pipeline. The "product" is the skill folders and agent files.
- The rules exist to stop AI output from drifting and from **quietly getting simpler** with each pass.
  That is why every 禁止簡化 rule matters more than it looks.
- Human-facing overview, directory tree and install steps: [README.md](README.md). Agents: [agents/README.md](agents/README.md).

## Layout (short)

```
<category>/elf-<name>/SKILL.md     team skills (stack, frontend, frontend/design, api, backend,
                                   desktop, cicd, testing, mcp, workflow)
<category>/<name>/                 third-party skills (not elf-*)
tools/                             third-party tooling skills
agents/*.md                        team agents (copied to ~/.claude/agents by scripts/sync-agents.sh)
skillshare/                        skillshare's built-in skill — tracked (see below)
frontend/design/ui-ux-pro-max/     tracked third-party skill, installed from an upstream subdir
_superpowers/                      tracked repo obra/superpowers (own .git, gitignored)
scripts/validate.sh                run before every commit
scripts/sync-agents.sh             install agents into Claude Code
scripts/release-ff.{sh,ps1}        maintainer release: fast-forward dev → release → main
docs/                              screenshots only — not a skill
```

A folder is a skill only if it contains `SKILL.md`; that is why `docs/`, `scripts/` and `agents/`
need no entry in `.skillignore` (it only holds `skillshare`).

### Nested paths auto-flatten on sync

`frontend/elf-vue/` → `~/.claude/skills/frontend__elf-vue/`. Nesting is not limited to two levels:
`frontend/design/ui-ux-pro-max/` → `frontend__design__ui-ux-pro-max`.
The `__` separator is generated by skillshare; **never** put `__` in a folder name yourself.
Agent `skills:` lists use the flattened name.

## Tracked content — do not hand-edit

Four paths are **not ours**: skillshare pulls them from upstream and records their commit plus
per-file hashes in `.metadata.json` (`entries`). Local edits there are silently undone on the next
update and make `skillshare status` report drift.

| Path | Upstream | Update with |
|---|---|---|
| `_superpowers/` | `obra/superpowers` | `skillshare update _superpowers` |
| `frontend/design/ui-ux-pro-max/` | `nextlevelbuilder/ui-ux-pro-max-skill`, subdir `.claude/skills/ui-ux-pro-max` | `skillshare update frontend/design/ui-ux-pro-max` |
| `frontend/vue/shadcn-vue/` | `noartem/skills`, subdir `skills/shadcn-vue` | `skillshare update frontend/vue/shadcn-vue` |
| `skillshare/` | `runkids/skillshare`, subdir `skills/skillshare` | `skillshare upgrade --skill` |

`frontend/vue/shadcn-vue/` was a hand copy of `noartem/skills@249519a` from 2026-05 until E-253 reinstalled
it as a tracked subdir. Other third-party folders may still be hand copies — check `.metadata.json`
before assuming a folder updates itself.

`_elf-dev/` (the old `elf-express/org-skills` checkout) was removed on 2026-10-04 with
`skillshare uninstall _elf-dev`: all 11 of its skills were disabled and superseded by the `elf-*` ones
(e.g. its 29-line `backend/dotnet` became the 361-line `backend/elf-dotnet`). Re-add it only if you need
the history: `skillshare install https://github.com/elf-express/org-skills.git`.

### No application code lives here

`elf-express/mcp-library` used to sit here as a git submodule. It was removed: this repo holds the
**ruler**, not the workpiece. The three `mcp/elf-mcp-*` skills reference it by repo name only
(`> 參考實作：elf-express/mcp-library …`) and never by path, so nothing depended on the checkout —
even their `references/simplification-evidence.md` was produced from a separate clone. Meanwhile the
submodule made `skillshare audit` walk a whole application as a skill group and fail `validate.sh`.

So: work on mcp-library in its own clone and its own PR. The same reasoning applies to any future repo
the skills describe — reference it by name, put the evidence in `references/`, do not vendor it.

`mcp-library/` is in `.gitignore`, so a clone parked here is never committed. It is **not** hidden from
`skillshare audit`, which has no ignore mechanism and walks whatever sits in the source tree
(`.skillignore` does not apply to it). A copy left on disk here keeps `validate.sh` red — keep the
working clone outside this repo.

Only `_superpowers` tracks a whole repo. Everything else is installed from the skill's own subdirectory
(`entries.<path>.subdir`), so an update can never pull more than that one folder. `validate.sh` fails
on an entry with no `subdir` that is not in its `WHOLE_REPO_ALLOWED` list. `ui-ux-pro-max` was recorded
as the whole `Yeachan-Heo/oh-my-claudecode` repo from the start; the 2026-10-01 update then replaced it
with 1,925 files and 43 unrelated skills (E-249).

`.metadata.json` can also hold `audit_accepted` — hashes of `skillshare audit` findings already reviewed
and accepted. It is currently absent (its only entries belonged to the removed oh-my-claudecode bundle), so
any finding is genuinely new.

## Writing or editing a team skill

1. Path `<category>/elf-<name>/SKILL.md`; folder name == frontmatter `name:`.
2. Frontmatter: `name`, `description` (繁中, one sentence + explicit 觸發條件), `metadata.version`, `metadata.owner: Elf Express`.
3. Body in 繁體中文（台灣）, code in English. Sections: 何時使用 · 固定規則 (numbered MUST / MUST NOT, each with WHY) ·
   標準範本 (copy-pasteable) · 禁止簡化 · 檢查清單 · 常見錯誤 · 待確認.
4. **Never guess.** Anything not verified against a real project goes under 待確認.
5. Version numbers live only in `stack/elf-stack`; other skills reference it.
6. Keep SKILL.md ≲ 400 lines; long templates go in `references/` or `templates/`.
7. **Do not simplify existing rules** — removing a rule, template step, check or 禁止簡化 item needs an explicit reason in the PR.
8. Back a 禁止簡化 rule with evidence where you can: the `mcp/elf-mcp-*` skills keep a
   `references/simplification-evidence.md` — a table whose every row cites a real commit or file plus a
   command that reproduces it. A row without evidence does not belong in the table; it belongs in 待確認.
9. Run `bash scripts/validate.sh`, then `skillshare sync --dry-run` to confirm names.

Edits to existing files are live immediately (targets are symlinks). `skillshare sync` is only needed when adding,
removing or renaming a skill folder, or changing `.skillignore`.

## Validation

`bash scripts/validate.sh` is the closest thing this repo has to a test suite. It needs
`python3`/`python`, and checks **every** `SKILL.md` — the tracked third-party ones
included:

- frontmatter exists and has `name` + `description`
- no folder name contains `__`
- `.metadata.json` parses as JSON
- every `.metadata.json` entry has a `subdir` or is in `WHOLE_REPO_ALLOWED`
- `_superpowers/` has no tracked files (a gitignored repo must never get committed)
- no `bin/` or `obj/` directory exists anywhere in the tree. `.gitignore` keeps them out of commits,
  but `skillshare sync` copies a skill folder whole, so a `dotnet restore` run inside a `templates/`
  folder would ship `obj/` to every target
- `skillshare sync --dry-run` and `skillshare audit --yes --no-tui --quiet` both succeed
  (skipped with a warning when the CLI is absent — a pass there is not proof)

CI (`.github/workflows/validate.yml`) runs the same script on every push to `dev`, `release` and
`hotfix/**` and on every PR, so the commit a release fast-forwards to has a check run (elf-team-rule
rule 28). It installs skillshare at `SKILLSHARE_VERSION` (keep it at the team's version; the checksum is
read from that release's `checksums.txt`) and points it at the checkout, so the sync/audit checks really
run there. CI has no `_superpowers/` checkout and reports 46 folders; that is expected.
That 46 is validate's count as well. CI has no `.skillignore.local`, so the per-machine exclusions in the
caveats below never apply there.

It does **not** check the 繁中 body sections, `metadata.version` / `owner`, the ≲400-line limit, the
no-guessing rule, or anything under `agents/`. Those are on the author and on PR review. There is no
per-skill runner: to check one skill, read it against the section list above, then run
`skillshare sync --dry-run` to confirm its flattened name.

Three caveats before you treat a red result as your own doing:

- Its `find` excludes only `.git/` and `node_modules/`, so any extra copy of the tree that lands in the
  repo (Kilo Code's `.kilo/worktrees/` used to do this) is validated too. With no such copy present and
  `_superpowers/` checked out it reports 61 folders. That is validate's count (`_superpowers/` included),
  not the number that syncs: with `.skillignore.local` exclusions in effect on the maintainer's machine
  (E-303, 2026-10-17: `/frontend/design/ui-ux-pro-max` and `/tools/agent-browser`), 59 actually sync.
  CI does not read `.skillignore.local`, so its count is unaffected.
- Its `skillshare sync --dry-run` and `skillshare audit` read your global skillshare config, so they check
  your configured **source** clone, not necessarily the tree you are validating. In a feature worktree,
  run it as `XDG_CONFIG_HOME=<worktree config> bash scripts/validate.sh` (see Gotchas).
- `skillshare audit` can exit non-zero on a clean tree. Run `skillshare audit` and compare before
  blaming a change.

## Agents

Agents are **copied**, not symlinked: Claude Code does not load symlinked agent files, and skillshare's agent
copy mode prunes plugin agents it doesn't manage. After editing `agents/*.md`, run `bash scripts/sync-agents.sh`
(`--dry-run` previews; it never deletes anything at the destination). Do **not** run `skillshare sync agents`
for these. Changes need a new Claude Code session to show up.

Frontmatter contract (full table and rationale: [agents/README.md](agents/README.md)):

- `tools:` — only what the role needs. Read-only roles (`elf-reviewer`, `168-devils-advocate`,
  `168-format-checker`) get no `Edit` / `Write` / `Bash`.
- `model: inherit` on every `elf-*` agent.
- `skills:` — **flattened** names (`frontend__elf-vue`), 3–6 that are needed every time. Everything else
  goes in the README's 需要時再載入 column, so the agent loads it through the Skill tool instead of
  spending context up front.
- `skills:` applies to **subagents** only. Agent-team teammates
  (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`) ignore it and must call the Skill tool themselves.

`agents/` also holds four `168-*` agents (OPNsense doc translation review). They are unrelated to the
`elf-*` conventions and preload no skills — do not reshape them to match the `elf-*` pattern.

## Branch workflow

動手前先讀 BRANCHING.md，依 elf-team-rule 規範操作分支。

This repo is type 3 (own project) in `workflow/elf-team-rule`. Branches move one way, by fast-forward only:
feature branch → PR → `dev` → `release` → `main`.

| Branch | Role |
|---|---|
| `dev`     | integration — feature branches (`feat/e-<id>-<name>` etc.) merge here via PR; GitHub default branch |
| `release` | the only stable version — teammates' skillshare sources sit on it; fast-forwarded from `origin/dev` |
| `main`    | 主庫 — the protected main line and the external baseline; only fast-forwarded from `origin/release`, never committed to, never used as the stable version or install source (renamed from `master` on 2026-10-11) |

```bash
git fetch origin
git log --oneline origin/release..origin/dev     # show what is about to ship
git switch release && git merge --ff-only origin/dev     && git push origin release
git log --oneline origin/main..origin/release
git switch main    && git merge --ff-only origin/release && git push origin main
```

`scripts/release-ff.sh` (Git Bash) and `scripts/release-ff.ps1` (Windows PowerShell 5.1 / PowerShell 7) run the
same steps with the rule 24 and 28 checks (commit list, check runs on `origin/dev`) and ask for the first 8 characters
of the SHA before each push; `--dry-run` / `-DryRun` only checks. They are for the maintainer: the rule below still
applies to AI agents.

Do **not** commit on `main` or `release` — it breaks the FF chain. AI agents open a feature branch and a PR; they never push to `dev`, `release` or `main`.

When `--ff-only` refuses, the target carries commits the source never saw — report that instead of forcing anything.

A clone made before the rename still has a local `master`: `git branch -m master main && git fetch origin && git branch -u origin/main main`.

## Gotchas

- `.metadata.json` is skillshare-managed — do not hand-edit. It holds per-file hashes (~11 KB; it was
  ~900 KB while the oh-my-claudecode bundle was tracked); seeing it in a diff after any
  `skillshare update` / `upgrade` is normal.
- `.skillignore.local` (not in git) holds per-machine overrides; `!/skillshare` must stay anchored with `/`, otherwise copies of `skillshare/` inside tool worktrees (e.g. `.kilo/worktrees/*`) get synced as skills.
- In `.skillignore` / `.skillignore.local`, a rule with a trailing `/` (e.g. `frontend/design/ui-ux-pro-max/`)
  does not exclude the skill folder itself under skillshare v0.25.13; write it as
  `/frontend/design/ui-ux-pro-max`. A trailing `/` only works for a parent directory such as `.ocrca/`
  (E-303, tested 2026-10-17).
- Git commands that print paths (`git ls-files`, `git status`, `git diff --name-only`, `git grep -l`, …)
  escape Chinese paths as octal by default (`"\346\..."`), so a `grep` piped after them silently misses
  those files. Run such commands as `git -c core.quotepath=false …` (or use `-z`). Plain `grep` / `rg` are
  not affected, and counting lines only (`| wc -l`) is not affected either (E-308).
- VS Code's Kilo Code extension creates `.kilo/worktrees/` full repo copies; they are ignored. Remove them with `git worktree remove`, never by editing.
- Windows: Git `core.symlinks=false` turns symlinks in upstream repos into small text files (e.g. `ui-ux-pro-max/scripts`). Replace them with the real directories when a skill depends on them.
- Your skillshare **source** may not be the clone you are working in. On a teammate's machine
  `sources.skills` in `~/.config/skillshare/config.yaml` points at the clone on `release`, so a bare
  `skillshare install` / `uninstall` / `update` changes `release`. To change tracked content, run every
  skillshare command from a feature worktree with a throwaway config (`targets: {}` syncs nowhere):
  ```bash
  WT_CFG=$(mktemp -d); mkdir -p $WT_CFG/skillshare
  # Run one of the two printf lines.
  # Git Bash (Windows): Windows skillshare rejects /e/… paths ("source path does not exist", E-311 step 2)
  printf 'sources:\n  skills: %s\nmode: merge\ntargets: {}\n' "$(pwd -W)" > $WT_CFG/skillshare/config.yaml
  # Other environments (Linux, macOS):
  printf 'sources:\n  skills: %s\nmode: merge\ntargets: {}\n' "$PWD" > $WT_CFG/skillshare/config.yaml
  XDG_CONFIG_HOME=$WT_CFG skillshare uninstall <path> --dry-run
  ```
  Check out `_superpowers/` in that worktree first (it is gitignored, so a fresh worktree lacks it):
  without it skillshare silently drops the `_superpowers` entry from `.metadata.json`.
- After updating anything tracked, read `git diff --stat` before committing. A jump in file count means
  the entry pulled more than its skill — stop. `validate.sh` also fails on an entry without a `subdir`.
- Uninstall a tracked path with `skillshare uninstall <path>`, not `--group <path>`: `--group` removes
  only the `SKILL.md` folders and leaves the rest of the bundle behind.
- Line endings: `core.autocrlf`; the "LF will be replaced by CRLF" warning is harmless.
- VS Code's C# Dev Kit would otherwise build a solution from `cicd/elf-cicd-backend/templates/*.csproj`
  and restore it: the restore fails (the template has no `TargetFramework` on purpose) and leaves an
  `obj/` that fails `validate.sh`. `.vscode/settings.json` turns that off; keep it.
