# Spec 驗收條件與步驟 6 的對照驗證

本文件補 `SKILL.md` 步驟 1 第 6 項（驗收條件的寫法）與步驟 6 第 4 項（測試全綠後對照 Spec），以及同一個 Spec 拆成多張 Plan 時，每張 Plan 驗證到哪裡為止（E-136）。
評測案例在 `evals/workflow__elf-linear-superpowers/`。

## 一、驗收條件：新增／修改／移除三組

Spec 的「驗收條件」MUST 依變更性質分成三組，每組沒有項目就寫「無」，不刪標題：

```markdown
## 驗收條件

### 新增
- [ ] <新行為>。情境：<前提> → <動作> → <結果>。

### 修改
- [ ] <新行為全文>（舊值／舊行為：<原本是什麼>）。情境：<前提> → <動作> → <結果>。

### 移除
- [ ] 不再提供 <功能>。原因：<為什麼拿掉>；遷移方式：<既有使用者或資料怎麼處理，沒有就寫「無」>。情境：<前提> → <動作> → <結果>。
```

1. **每一條至少一個「前提 → 動作 → 結果」情境**，結果寫成可以直接驗的值或畫面狀態。
   為什麼：陳述句（「使用者可以綁定 TOTP」）沒說通過長什麼樣子，步驟 6 只能憑感覺勾。
2. **修改那組寫新行為全文，並註明舊值**（例：「閒置 15 分鐘登出（舊值 30 分鐘）」）。
   為什麼：只寫新值，審的人看不出這是改既有行為，測試也不會去驗舊行為已經不在。
3. **移除那組寫原因與遷移方式**；兩者 Spec 沒寫、只有使用者能答時，列進「待決問題」問使用者，不自己補。
   為什麼：拿掉功能會影響已經在用的人，遷移方式是使用者的決定。
4. **平鋪清單不能定案。** 驗收條件還是平鋪條列、沒有情境、修改沒寫舊值時，步驟 1 第 6 項自審不通過，不留「規格已定案」，使用者說過「沒問題」也一樣。先補成三組，再請核准者看**補完之後**的版本，核准的是那一版。
   為什麼：核准只涵蓋核准者看過的內容；拿平鋪版的「沒問題」去定案補過的版本，等於替使用者核准他沒看過的東西。
5. Plan 群組（`SKILL.md` 步驟 3「同一個 Spec 底下增加 Plan」）：每一條結尾照舊標由哪張 Plan 勾，例 `（E-387）`。

## 二、測試全綠後對照 Spec：完整性、正確性、一致性

步驟 6 第 4 項回 Spec 時，MUST 對照三件事，**核對範圍不只「驗收條件」**：

| 面向 | 對照什麼 | 怎麼判 |
|---|---|---|
| 完整性 | Spec「範圍（要做）」每一項、每一條驗收條件 | 每一項都有對應的變更與證據；任何一項沒有實作或沒有證據就不通過 |
| 正確性 | 驗收條件的情境 | 證據裡的值與情境的結果一致（數量、時間、狀態照抄 Spec 的值比對） |
| 一致性 | Spec「已決定的做法」每一項 | 實作照決定的做法做；換了儲存位置、套件、介面就不通過，測試全綠也一樣 |

1. 每個面向的結論都附證據：`檔案:行` 或指令輸出（含 exit code）。
   為什麼：「測試全綠」只證明測試寫到的部分；範圍裡有、驗收條件漏寫的項目，測試不會替你發現。
2. **任何一項不通過，這次驗證就不通過**：不勾那一條、不宣告完成、不說可以開 PR，使用者催促也一樣；下一步是照步驟 6 第 4 項回 S2 修好再驗。
   為什麼：保險②（步驟 6）就是最後一道對照，放行一次，缺口就跟著進 `dev`。
3. 不符的是「已決定的做法」時，下一步只有兩種：改回符合決定的做法；或認為決定本身要改，就依步驟 4「需要改規格」停下來問使用者，使用者同意後才回 Spec 修改。MUST NOT 自己改 Spec，也 MUST NOT 用裁決（`Ruling:`）把這個決定結掉。
   為什麼：「Eddie 決定」的項目只有 Eddie 能改；裁決只處理計畫裡沒寫的細節，不處理推翻 Spec。

## 三、同一個 Spec 拆成多張 Plan 時的驗證邊界

### 1. 只驗自己那張

非最後一張的 Plan 跑步驟 6 時，結論只對結尾標本 Plan 的驗收條件與本 Plan 負責的範圍下判斷：

- 別張 Plan 的條件逐條寫出歸哪一張、還沒到它驗證的時候；不列為本 Plan 的缺口，不代勾、不代驗（`SKILL.md` 步驟 6 第 4 項、規則 33）。
- 本 Plan 自己的證據（步驟 6 第 3 項「合進 `dev` 前」那段、步驟 5-1 審查）齊了，就判定可以交接：後一張可以從本 Plan 的完成點開分支。不等後一張做完，也不替後一張做它的範圍。
- 本 Plan 自己的證據不齊時，照實寫缺哪一項，補齊前不算完成點；這跟別張 Plan 的進度無關。

為什麼：疊加分支要求前一張先到完成點（步驟 2 第 3 項）；把後一張的項目算成前一張的缺口，群組永遠開不了下一張。

### 2. 沒有任何 Plan 認領的範圍：停下，到 Spec 問

對照時發現 Spec「範圍（要做）」有一項沒有任何 Plan 認領——沒有驗收條件標到任何 Plan，也沒有任何 Plan 的 Task 覆蓋——MUST：

1. 停下，在驗證留言寫出是哪一項、為什麼判定沒人認領（各 Plan 的目標、驗收條件標記、Task 都查過）。
2. **在 Spec（父 issue）留言**請使用者決定：補進哪一張 Plan（含補驗收條件並標上 Plan 編號），或移到「不做」／另開 Spec＋Plan。本 Plan 的驗證留言只寫已轉到 Spec 問，並附那則留言。
3. MUST NOT 自己認下來（加進本 Plan 的 Task、自行實作）、MUST NOT 用裁決結掉、MUST NOT 當成「超出本 Plan 範圍」就不回報。

為什麼：範圍歸哪張 Plan 是 Spec 層級的決定，問題只留在某張 Plan 的留言，其他 Plan 與審計員看不到；沒人回報的話，全組驗收條件都勾滿、Spec 自動關閉，那一項卻沒做也沒驗。

### 3. 疊加順序最後一張：整份 Spec 再驗一次

疊加順序最後一張 Plan 的步驟 6，MUST 對**整份 Spec** 再跑一次第二節的三個面向，包括前面 Plan 標的驗收條件與範圍，每一項附證據：

- 前面 Plan 的條件已經勾過也要重驗，證據以最後一張分支上的程式與指令輸出為準。
- 發現前面 Plan 的缺口，照 `SKILL.md` 步驟 4「Plan 群組裡發現前面 Plan 的問題」在最後一張分支上修，並在那張 Plan 留言。
- 整份 Spec 完整驗過、沒有缺口，才開整合 PR；有缺口時不說可以開。

為什麼：整合 PR 是群組唯一進 `dev` 的入口；前面各張只驗自己那段，疊加後互相覆蓋或漏接只有最後一張看得到。
